## Purpose

This exploratory batch evaluates the third predefined failure class: the API
remains live and its database remains healthy, but order requests return HTTP
500 because a controlled application fault is active.

## Configuration

- Date: 10 August 2026
- Trials: 3
- Fault class: `http_500_failure`
- Root cause: `forced_application_error_mode`
- Fault duration: 8 seconds
- Cooldown between trials: 8 seconds
- Workload: one simulated order request per second
- Detector: `operations-health-rule-v2`
- Metrics window: 5 seconds
- Rule threshold: at least 2 HTTP 500 responses and error rate >= 0.5
- Ground-truth timing source: application `changed_at`

## Example detection evidence

The first detection was created from the following five-second window:

```json
{
  "total_requests": 5,
  "http_500_count": 3,
  "http_500_rate": 0.6
}
```

After the final fault ended, the same window contained five successful
requests, zero HTTP 500 responses, and an HTTP 500 rate of 0.0.

## Interpretation

The rule detector correctly identified application failures while liveness and
database health remained normal. Detection latency was consistent because the
rule requires enough failed workload requests to populate the metrics window.
Recovery detection is intentionally delayed until older HTTP 500 events leave
the five-second window.

## Limitations and next steps

- Three trials validate the pipeline but do not support statistical inference.
- The application fault is intentionally controlled and repeatable.
- The threshold was selected before this batch and must remain fixed for fair
  comparison with later methods.
- All current batches contain one fault class at a time. The next experiment
  should randomise the three fault types in a mixed batch.
- A no-fault observation period is required to estimate false positives under
  normal traffic.

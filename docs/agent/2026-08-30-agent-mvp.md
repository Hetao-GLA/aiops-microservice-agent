# Human-approved operations Agent MVP

> Historical design record. For current UI labels and a controlled demo, use
> [Getting started](../GETTING_STARTED.md). Optional planner dependencies must be
> installed before selecting that mode. Timed fault injection in this old guide
> restores the fault automatically, so recovery after its timer alone does not
> demonstrate Agent execution. See [reproduction boundaries](../REPRODUCIBILITY.md).

Date: 2026-08-30  
Status: implemented and unit-tested; operational-effect evaluation is pending.

## Purpose and boundary

The Agent turns an existing fault diagnosis into an explainable, operator-
approved recovery workflow. It is a host-side control plane rather than a
fully autonomous administrator. It supports the three controlled local fault
classes already used by the experimental platform:

| Fault | Locked recovery action | Verification |
|---|---|---|
| `database_connection_failure` | `docker compose start database` | liveness and database health |
| `service_stopped` | `docker compose start api` | liveness and database health |
| `http_500_failure` | disable the controlled HTTP-500 flag | flag disabled, liveness and database health |

The implementation demonstrates an Agent/Runbook/approval mechanism. It does
not yet demonstrate that an LLM improves diagnosis, operator decisions or
mean time to recovery (MTTR). Those claims require a separately registered
comparison experiment.

## Architecture

```text
health / metrics / logs / detections
                |
                v
       read-only evidence tools
                |
                v
 deterministic or OpenAI planner ----> explanation
                |
                v
     validated local Runbook + policy
                |
                v
          human approval gate
                |
                v
       allow-listed recovery executor
                |
                v
       independent health verification
                |
                v
     incident JSON + append-only audit log
```

The Agent runs on the host at port 8100. This is intentional: it remains able
to start the existing `api` or `database` container after that container has
been stopped. The business application remains in Docker on port 8000.

## State machine

```text
diagnose -> awaiting_approval -> approved -> executing -> verifying -> resolved
                    |                          |              |
                    v                          v              v
                 rejected             execution_failed  verification_failed
                                                               |
                                                               v
                                                        retry verification
```

Only an incident in `approved` state with a positive approval record may enter
the executor. Rejection is terminal. A failed verification may be retried
without repeating the recovery action.

## Safety controls

- The planner receives only five read-only tools: current health, current
  metrics, bounded Compose log tails, recent structured detections and one
  local Runbook.
- Recovery actions are not exposed as model tools. A model recommendation is
  advisory and cannot replace the action locked to the diagnosed fault.
- The executor does not invoke a shell. It constructs fixed argument lists and
  permits only `docker compose start api`, `docker compose start database`, or
  the fixed HTTP-500 control request.
- Every execution requires an explicit named human approval.
- Recovery success is not inferred from command completion; existing health
  endpoints must pass afterward.
- Incident snapshots are stored under `data/agent/incidents/`. State changes
  are also appended to `data/agent/audit.jsonl`.
- API keys are read from environment variables and are never written to the
  repository or Agent incident records.

The optional model adapter follows the OpenAI
[Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)
and its documented
[function-calling flow](https://developers.openai.com/api/docs/guides/function-calling).
Tool outputs are returned to the model only for read-only evidence functions.

## Start the Agent

Start Docker Desktop and the research platform first:

```powershell
docker compose up --build
```

In a second PowerShell window, from the repository root:

```powershell
.\.venv\Scripts\python.exe -m ops_agent
```

Open:

- Agent console: <http://127.0.0.1:8100/>
- Agent API: <http://127.0.0.1:8100/docs>
- Safety/status endpoint: <http://127.0.0.1:8100/agent/health>

The default deterministic planner requires no external API and is the
recommended mode for reproducible demonstrations.

## Optional OpenAI explanation planner

Install the optional dependency:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-agent.txt
```

Set credentials only in the current environment, using a model available to
the account:

```powershell
$env:OPS_AGENT_PLANNER = "openai"
$env:OPENAI_API_KEY = "<your-api-key>"
$env:OPENAI_MODEL = "<available-model-id>"
.\.venv\Scripts\python.exe -m ops_agent
```

If the key, model or API call is unavailable, the factory uses the
deterministic planner. The recovery policy and approval gate are identical in
both modes.

## Demonstration procedure

1. Keep the Docker platform and host-side Agent running.
2. Inject one 60-second controlled fault from a third PowerShell window. For
   example:

   ```powershell
   .\.venv\Scripts\python.exe -m experiment.fault_injector `
       database_disconnect `
       --duration 60
   ```

3. In the Agent console, select **Diagnose current fault**. Confirm that the
   evidence, fault label and locked Runbook action are reasonable.
4. Enter the operator name and an approval note, then select **Approve**.
5. Select **Execute approved recovery**. The Agent starts only the database
   service and then polls the existing liveness and database-health endpoints.
6. Confirm that the state becomes `resolved`. Expand the incident details to
   show diagnosis, approval, fixed action, verification checks and audit
   metadata.
7. Repeat with `service_stop` and `http_500` if a full three-fault
   demonstration is required.

Do not execute recovery when using a submitted diagnosis as a dry-run unless
the corresponding fault is actually active. The live diagnosis path is the
preferred software demonstration.

## API summary

| Method and path | Purpose |
|---|---|
| `GET /agent/health` | show planner and safety boundary |
| `GET /agent/runbooks` | list validated local Runbooks |
| `GET /agent/incidents` | list persisted Agent incidents |
| `POST /agent/incidents/diagnose` | collect/read evidence and create proposal |
| `GET /agent/incidents/{id}` | inspect one complete incident |
| `POST /agent/incidents/{id}/approval` | approve or reject the proposal |
| `POST /agent/incidents/{id}/execute` | execute only an approved fixed action |
| `POST /agent/incidents/{id}/verify` | retry a failed verification |

## Evaluation still required

To make the Agent a research result rather than only an engineering result,
freeze a new protocol before collecting evidence. A suitable design would
compare manual-only and Agent-assisted operation on unseen incident runs using
the same operators and counterbalanced ordering. Record diagnosis correctness,
unsafe-action rate, approval agreement, time to correct diagnosis, execution
success, verification success and end-to-end MTTR. The current local
three-fault task may be too easy to show an accuracy gain, so time, safety and
explanation usefulness are more credible primary outcomes.
